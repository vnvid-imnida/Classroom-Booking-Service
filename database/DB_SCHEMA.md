# Схема базы данных для системы бронирования аудиторий

## 1. Цели проектирования

Схема должна покрывать:
- отображение занятости аудиторий (сетка расписания);
- поиск аудиторий по атрибутам;
- подачу заявки на бронирование;
- двухэтапную модерацию заявок;
- личный кабинет преподавателя (активные/архивные брони, отмена, перенос);
- интеграцию с `https://ruz.spbstu.ru/` так, чтобы слоты официального расписания блокировали ручные бронирования.

Дополнительно:
- схема нормализована (до 3NF/BCNF там, где это практически уместно);
- заложены ограничения целостности и индексы для типовых запросов.

## 2. Ключевая идея модели

Один и тот же временной слот может быть занят из двух источников:
- ручное бронирование (после подтверждения модератором);
- официальный слот из RUZ.

Чтобы не допустить конфликтов между ними, используется единая таблица `bookings` с полем `source` (`MANUAL` или `RUZ`).

Это позволяет одним ограничением запретить пересечения по времени в одной аудитории.

## 3. ER-модель (связи)

```text
users (1) ----------------------< booking_requests >---------------------- (1) rooms
  ^                                  |   ^                                  ^
  |                                  |   |                                  |
  |                                  |   +------ event_purposes -----------+
  |                                  |
  +------------------------< bookings >----------------------------- (1) rooms
                                 |
                                 +------------------< ruz_sync_runs (для source=RUZ)

buildings (1) -------------------< rooms
```

## 4. Таблицы и обоснование полей

### 4.1 `users`

Назначение: единый справочник пользователей (преподаватель, модератор, администратор, системный пользователь импорта).

Поля:
- `id` (PK, UUID): стабильный внутренний идентификатор.
- `telegram_id` (UNIQUE): числовой ID пользователя Telegram.
- `telegram_username` (UNIQUE): username пользователя Telegram (например, `@Koshsky`).
- `full_name`: отображаемое имя.
- `role`: роль в бизнес-процессе.
- `is_active`: мягкое отключение без потери истории.
- `created_at`: аудит.

Почему так:
- отделяем внешний Telegram ID (`telegram_id`) от внутреннего PK, чтобы не ломать связи при изменениях в интеграции и авторизации.

### 4.2 `buildings`

Назначение: справочник корпусов.

Поля:
- `id` (PK), `code` (UNIQUE), `name`, `address`, `created_at`.

Почему так:
- фильтрация по корпусу требуется явно;
- хранение корпуса отдельно исключает дублирование названия/адреса в каждой аудитории.

### 4.3 `rooms`

Назначение: справочник аудиторий и параметров фильтрации.

Поля:
- `id` (PK), `building_id` (FK), `room_number`, `floor`;
- `capacity`;
- `has_projector`, `has_whiteboard`, `is_accessible`;
- `is_active`, `created_at`;
- `UNIQUE(building_id, room_number)`.

Почему так:
- все поля из требований поиска вынесены сюда;
- `UNIQUE(building_id, room_number)` исключает дубликаты одной аудитории;
- `is_accessible` относится именно к аудитории и означает безбарьерный доступ для маломобильных групп;
- boolean-поля сознательно оставлены в таблице, потому что список признаков фиксирован требованиями и не требует EAV/многие-ко-многим.

### 4.4 `event_purposes`

Назначение: справочник целей мероприятия (`Лекция`, `Экзамен`, `Собрание`).

Поля:
- `id` (PK), `code` (UNIQUE), `name` (UNIQUE), `is_active`.

Почему так:
- цель вынесена в справочник вместо free-text: меньше ошибок ввода, проще аналитика;
- при расширении списка целей не нужна миграция ENUM.

### 4.5 `booking_requests`

Назначение: жизненный цикл заявки до финального решения модератора.

Поля:
- `id` (PK);
- `requester_id` (FK -> `users`);
- `action` (`CREATE` / `RESCHEDULE`);
- `target_booking_id` (nullable FK -> `bookings`, нужен только для `RESCHEDULE`);
- `room_id`, `purpose_id`, `title`, `description`, `starts_at`, `ends_at`;
- `status` (`DRAFT`, `PENDING`, `APPROVED`, `REJECTED`);
- `submitted_at`, `moderated_by`, `moderated_at`, `moderation_comment`;
- `created_at`, `updated_at`.

Почему так:
- статусы полностью соответствуют требованию двухэтапной модерации;
- `action + target_booking_id` позволяет перенос без отдельной таблицы "запросов на перенос";
- хранение временного интервала в заявке нужно, чтобы согласование велось по конкретному слоту.

Ограничения:
- `ends_at > starts_at`;
- для `CREATE` запрещен `target_booking_id`, для `RESCHEDULE` обязателен;
- `PENDING` требует `submitted_at`;
- `APPROVED/REJECTED` требуют `moderated_at` и `moderated_by`.

### 4.6 `ruz_sync_runs`

Назначение: журнал запусков синхронизации с RUZ.

Поля:
- `id` (PK), `started_at`, `finished_at`;
- `status` (`RUNNING`/`SUCCESS`/`FAILED`);
- `source_url`, `imported_slots_count`, `error_message`.

Почему так:
- таблица нужна для наблюдаемости и отладки интеграции;
- можно быстро понять, почему официальные слоты не обновились.

### 4.7 `bookings`

Назначение: фактически занятые слоты, которые блокируют аудиторию.

Поля:
- `id` (PK);
- `request_id` (nullable, UNIQUE FK -> `booking_requests`), только для ручных подтвержденных заявок;
- `organizer_id` (nullable FK -> `users`), обязателен для ручных броней;
- `room_id` (FK), `purpose_id` (nullable FK), `title`, `description`;
- `starts_at`, `ends_at`;
- `source` (`MANUAL` / `RUZ`);
- `status` (`ACTIVE`, `CANCELLED`, `RESCHEDULED`, `COMPLETED`);
- `external_event_id` (для RUZ), `sync_run_id` (FK -> `ruz_sync_runs`);
- `cancelled_by`, `cancelled_at`, `cancel_reason`;
- `rescheduled_to_booking_id` (self FK);
- `created_at`.

Почему так:
- единая таблица для MANUAL и RUZ нужна, чтобы технически обеспечить единый запрет пересечений;
- `request_id UNIQUE` гарантирует, что одна заявка порождает не более одной итоговой брони;
- отдельный `status` нужен для личного кабинета (активные/архивные) и истории отмен/переносов.

Ключевое ограничение:
- `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&) WHERE status='ACTIVE'`.

Этим запрещается пересечение активных слотов в одной аудитории независимо от источника (`MANUAL` или `RUZ`).

## 5. Почему некоторые сущности не добавлены

1. Отдельная таблица `time_slots` не добавлена.
Причина: расписание требует произвольные интервалы времени, а не фиксированные пары; отдельный справочник слотов усложнит переносы и интеграцию с RUZ.

2. Таблица "оборудование аудитории" many-to-many не добавлена.
Причина: требования содержат фиксированный список бинарных признаков (`проектор`, `маркерная доска`, `доступность`). Для этого boolean-поля проще и быстрее в фильтрации.

3. Отдельная таблица "approved_bookings" не добавлена.
Причина: это дублировало бы `bookings` и нарушало бы принцип единого источника истины по занятости.

4. EAV-модель для атрибутов аудитории не добавлена.
Причина: EAV усложняет индексацию и фильтрацию. При текущем фиксированном наборе атрибутов это избыточно.

## 6. Нормализация

### 6.1 1NF

- Во всех таблицах атомарные значения;
- Нет повторяющихся групп столбцов;
- Нет массивов для бизнес-атрибутов (кроме допустимого `jsonb`-подхода, который здесь не используется).

### 6.2 2NF

- Все таблицы имеют простой PK (не составной), поэтому частичных зависимостей от части ключа нет.

### 6.3 3NF

- `building_name/address` не дублируются в `rooms`;
- `purpose_name` не дублируется в `booking_requests` и `bookings`, хранится через FK;
- данные модерации хранятся в `booking_requests`, а не размазываются по нескольким сущностям;
- данные синхронизации вынесены в `ruz_sync_runs`.

### 6.4 BCNF (практически)

- Справочники (`buildings`, `event_purposes`) удовлетворяют BCNF;
- в операционных таблицах бизнес-ограничения выражены через `UNIQUE`, `CHECK`, `FK`, `EXCLUDE`.

## 7. Покрытие функциональных требований

1. Просмотр сетки расписания.
Решение: view `room_occupancy_grid` и таблица `bookings` (`status='ACTIVE'`).

2. Поиск и фильтрация аудиторий.
Решение: `rooms` + `buildings`, индекс `rooms_filter_idx`.

3. Создание заявки на бронирование.
Решение: `booking_requests` со статусом `DRAFT/PENDING`, полями времени и цели.

4. Модерация заявок (двухэтапная).
Решение: `booking_requests.status` + поля модерации; бронь считается финальной после создания записи в `bookings` с `source='MANUAL'`.

5. Личный кабинет преподавателя.
Решение: выборка из `bookings` по `organizer_id`; активные/архивные определяются по `status` и времени.

6. Интеграция с RUZ.
Решение: импорт слотов в `bookings` с `source='RUZ'`, аудит в `ruz_sync_runs`, уникальность внешнего события через `bookings_ruz_external_event_uidx`.

## 8. Важные бизнес-правила, которые лучше проверять в backend

1. Отмена/перенос преподавателем только если до начала более 24 часов.
Почему не `CHECK`: правило зависит от текущего времени и контекста пользователя, что надежнее и понятнее валидировать на уровне сервиса.

2. Разрешенные переходы статусов заявки (например, `DRAFT -> PENDING -> APPROVED/REJECTED`).
Можно хранить в сервисном слое или добавить state-machine таблицу/триггеры при усложнении процесса.

## 9. Примеры типовых запросов

### 9.1 Фильтрация аудиторий

```sql
SELECT r.*, b.code AS building_code
FROM rooms r
JOIN buildings b ON b.id = r.building_id
WHERE r.is_active = true
  AND r.capacity >= 40
  AND b.code = '2'
  AND r.floor = 3
  AND r.has_projector = true
  AND r.has_whiteboard = true
  AND r.is_accessible = true;
```

### 9.2 Свободные аудитории в интервале

```sql
SELECT r.id, b.code, r.room_number
FROM rooms r
JOIN buildings b ON b.id = r.building_id
WHERE r.is_active = true
  AND NOT EXISTS (
      SELECT 1
      FROM bookings bk
      WHERE bk.room_id = r.id
        AND bk.status = 'ACTIVE'
        AND tstzrange(bk.starts_at, bk.ends_at, '[)') && tstzrange($1, $2, '[)')
  );
```

### 9.3 Активные и архивные бронирования преподавателя

```sql
SELECT *
FROM bookings
WHERE organizer_id = $1
  AND source = 'MANUAL'
  AND (
      (status = 'ACTIVE' AND ends_at >= now())
      OR (status IN ('CANCELLED', 'RESCHEDULED', 'COMPLETED') OR ends_at < now())
  )
ORDER BY starts_at DESC;
```
